# サンドボックス自律境界契約（正本）

本書は **サンドボックスにおける自律の境界** のみを定義する。ランタイム実装・スケジューラの権限移譲・キュー運用の変更は本書のスコープ外であり、本書はそれらを規定しない。

---

## 1. 目的・適用範囲

- **目的**: サンドボックス作業において、ワーカーが取り得る自律行為の上限と、停止・失敗の判定に使う **文書上の不変条件** を一意に定義する。
- **適用範囲（本書のみ）**:
  - 自律の境界（何を自律にしてよいか／してはいけないか）
  - 停止（STOP）の意味と、観測可能な真偽条件
  - `failure_type` の語彙規則（`HOLD` の禁止を含む）
  - 境界違反の分類（`scope_violation`）
- **ランタイムからの分離（明示的非スコープ）**:
  - 実装コードの追加・変更・削除の指示は行わない（本契約は仕様文書のみ）。
  - **スケジューラの乗っ取り**（スケジューラの判断権限をワーカーが奪うこと）は禁止であり、本書はスケジューラの振る舞いを定義・変更しない。
  - **キュー・ランタイムの変更**（キュー投入規則・ワーカー数・実行順の実装変更）は本書のスコープ外とし、本書はキュー／ランタイム契約を変更しない。

---

## 2. 禁止される自律行為

次の行為は、サンドボックス自律として **禁止** する（いずれも「自律」とみなす）。

| ID | 禁止事項 | 意味（曖昧語なし） |
|----|-----------|-------------------|
| A1 | **自律 GO** | 人間の明示承認なしに、作業継続・再開・次工程開始をワーカーが単独で決定し実行すること。 |
| A2 | **ワーカー自己承認** | 人間のレビューを待たずに、ワーカーが自身の成果物を「承認済み」と同等の効果を持つ状態へ遷移させること。 |
| A3 | **main への push** | Git の `main`（または `master`）相当の既定本流ブランチへ、ワーカーが自律的に `push` すること。 |
| A4 | **自動マージ** | 人間の明示操作なしに、ワーカーがマージを完了させること（例: 自動マージ設定の利用、無人でのマージ完了）。 |
| A5 | **stash 操作** | `git stash` 系（保存・適用・ドロップ等）をワーカーが自律的に実行すること。 |

---

## 3. 停止の定義と決定的停止条件

### 3.1 「停止（STOP）」の意味

**STOP** とは、当該サンドボックス作業単位について、ワーカーが **新たな副作用的操作**（ファイル書き込み、Git 操作、外部 API 呼び出し等）を **これ以上開始しない** 終端状態である。

### 3.2 STOP が **真** であるための必要条件（全て満たす）

次の命題 `C1`, `C2` を評価し、**両方が真**のときに限り `STOP = true` とする。いずれかが偽なら `STOP = false`（未定義扱いは行わない）。

1. **C1（変更パスの閉包）**  
   - 観測集合 `P` を次で定義する: ワーキングツリーおよびインデックスに現れる **相対パス文字列** の集合（`git diff --name-only` と `git status --porcelain` から抽出し、行頭2文字を除いたパス名を正規化した結果の和集合）。  
   - 許可集合 `A` を、当該セッションの `allowed_changes` に列挙されたパス文字列の集合とする（Unicode 正規化後に **完全一致** で比較）。  
   - 命題: `P ⊆ A`（`P` の各要素が `A` に含まれる）。

2. **C2（禁止自律事象の非存在）**  
   - 観測集合 `F` を、当該セッション中に **監査ログまたは CI 出力に記録された** 操作イベントの識別子集合とする（記録が無い場合は `F = ∅` とみなす）。  
   - 禁止集合 `B = { autonomous_go, worker_self_approval, push_to_main, auto_merge, git_stash }`。  
   - 命題: `F ∩ B = ∅`（空集合）。

### 3.3 正常終了・異常終了との関係

- **正常終了**: `STOP = true` かつ `failure_type` は未使用、または空文字・ヌル相当として扱われる（セッション JSON の運用に従う）。  
- **異常終了**: `STOP = true` かつ **4. 節の許容語彙** に含まれる `failure_type` が **一つに確定**している（複数同時確定は禁止）。

---

## 4. `failure_type` 規則

### 4.1 `HOLD` は `failure_type` ではない

- 文字列 **`HOLD`** を `failure_type` の値として用いてはならない。  
- `HOLD` が出現した場合、それは **失敗型の確定**ではなく **人間判断待ちの運用状態** として別フィールドで表現する（本契約はそのフィールド名を規定しない）。

### 4.2 許容される `failure_type` 語彙（閉集合）

`failure_type` は次の **いずれか一つ** のみを取る（閉集合・小文字スネークケース）:

- `spec_missing` — 必要な仕様・セクション・キーが欠落している  
- `scope_violation` — 許可変更集合・禁止事項・自律境界に違反している  
- `test_failure` — テストが期待結果を満たさない  
- `dependency_missing` — 外部依存・入力成果物が欠落している  
- `environment_error` — 実行環境・権限・ネットワーク等のエラー  
- `contract_violation` — 本契約または当該セッション acceptance に明示された文書ルール違反  

上記以外の文字列を `failure_type` として用いてはならない。

---

## 5. 違反の分類

- **自律境界違反**（2. 節の禁止事項のいずれかに該当する行為が発生したこと）を検知した場合、そのセッションの `failure_type` は **`scope_violation`** に分類する。  
- 境界違反が複数あっても、`failure_type` は **`scope_violation` のみ** に正規化する（複数値の同時確定は禁止）。

---

## 6. 本契約の非対象（参照のみ）

- **`global_rules.md`** および **`master_instruction.md`** は、本契約セッション（文書起票）により **変更しない**。  
- 本書は上記ファイルを **参照のみ** とし、内容の改訂手順・版管理は本書のスコープ外である。
